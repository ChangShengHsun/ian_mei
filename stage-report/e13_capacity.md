# E13 · 這些結論是不是「小模型」的結論

2026-08-23 排入佇列。九次訓練（三個 arm × seed 0–2，base=32），約 40 小時。

**本報告第 0 到第 4 節寫在第一次 w32 訓練之前，一個結果都沒有。**
判準寫在 `exp/summarize_capacity.py`，該檔先跑過 `--selftest` 才排隊。

---

## 0. 這個系列一直沒回答的問題

`train.py` 的 U-Net 是 **117,393 個參數**。這個領域的標準大約是 3000 萬。
所以本系列的每一個結論都帶著同一個未檢驗的前提。

具體來說，有兩句話一直分不開：

| 我們量到的 | 分不開的另一種解釋 |
|---|---|
| stage 0 與 [[e5_label_noise]]：「loss 之間的差距比種子之間的差距還小」| **模型太小，小到 loss 起不了作用** |
| [[e14_augmentation]]：「給模型看什麼，勝過要求模型什麼」| **增強是在補償一個小到會過擬合二十張影像的模型** |

兩句都可以用同一個實驗分開：**把寬度乘 4，看差距怎麼變。**

## 1. 三個 arm，以及為什麼是三個

原本規劃的 E13 只有兩個（`A_dice_w32` vs `B_cldice_w32`），
因為當時要問的是 loss。[[e14_augmentation]] 之後，那個問題降級了，
更值得問的是增強的優勢會不會隨容量縮水。

| arm | 參數 | 問什麼 |
|---|---|---|
| `A_dice_w32` | 467,233 | 參考點 |
| `B_cldice_w32` | 467,233 | E13 原本的問題：有了容量之後，loss 開始有用了嗎 |
| `H_aug_w32` | 467,233 | E14 之後的問題：增強的優勢撐得住容量嗎 |

## 2. 要比的不是 w32 對 w32，是「差距對差距」

單看「w32 比 base16 好多少」沒有用——大模型當然比較好。
有意義的是**兩個 arm 之間的差距在寬度變化下怎麼動**，
所以每一條判準都是差之差，而且**在兩個寬度上各報一次**。

| | 差距 | 讀法 |
|---|---|---|
| **1** | `H_aug` − `A_dice`（最暗層）| 兩個寬度都成立 → 輸入端的重要性與容量無關；縮到零 → E14 是小模型結果 |
| **2** | `B_cldice` − `A_dice`（最暗層）| E13 原本的問題 |
| **3** | `H_aug` − `B_cldice`（最暗層）| 「輸入勝過 loss」的排序會不會翻轉 |
| **4** | `H_aug` − `A_dice`（最亮層）| [[e15_expected_run_length]] 說那層已在天花板 99%，所以那裡只有代價可看 |

**每個寬度自己的差距要過種子閘；「差之差」只報不判。**
三顆種子一邊的差之差，這個設計沒辦法誠實地訂一個門檻，
而看到結果之後才訂一個，正是這份檔案存在的目的所要防的事。

## 3. 一個排隊前就抓到的坑

`AUGMENTS` 是用**完整 config 名稱**當鍵的。
`base_width("H_aug_w32")` 會正確讀出 32，
但 `AUGMENTS.get("H_aug_w32")` 回傳 **空 tuple**——

**`H_aug_w32` 會完全不做資料增強地訓練完，而且仍然叫這個名字。**
沒有任何一步會報錯。這個實驗會安靜地變成「同一個 baseline 訓練兩次」。

在排隊之前抓到，補了 `AUGMENTS["H_aug_w32"]`，
並且把檢查寫進 `test_capacity.py`：
**每一個 `_w` 變體的 loss 與增強集合都必須等於它的 base**。

```
  A_dice_w32 matches A_dice: loss None, augments none
  B_cldice_w32 matches B_cldice: loss cldice, augments none
  H_aug_w32 matches H_aug: loss None, augments ('dihedral', 'jitter')
```

## 4. 成本是量的，不是猜的

CLAUDE.md 的規矩。實測（2 執行緒，另一個訓練工作佔著其餘核心）：

| | 參數 | s/step | 每個 run |
|---|---|---|---|
| base=16 | 117,393 | 0.328 | 2.8 h |
| base=32 | 467,233 | 0.946 | **8.2 h** |

**2.9 倍，不是參數比的 4 倍**——寬度對 CPU 時間是次二次的。
機器空著時 base=16 是 0.12 s/step，換算 w32 約 0.35，也就是每個 run 約 3 小時；
實際會落在中間，**九個 run 抓 40 小時**。

排列是**種子優先**（三個 arm 的 seed 0 先跑完，再 seed 1）。
所以中斷在任何一點，留下的是一組完整但吵的三方比較，
而不是一個被過度量測的 arm。每跑完一顆種子就重算一次判定。

## 5. 兩個限制

**一、三顆種子。** [[e14_augmentation]] 的判準 1 在六顆種子上仍然倒在
Q1 的變異上（五正一負，擋下它的是 −0.0021）。
這裡的判準也押在 Q1，而且只有三顆種子。
**差之差如果很小，這個設計答不出來，那時的正確反應是加種子。**

**二、4 倍不是 256 倍。** 117k → 467k 仍然離 3000 萬很遠。
這個實驗能回答「差距對容量敏感嗎」，
**不能回答「在一個真正大的模型上會怎樣」**。

## 6. 結果

九次訓練在 2026-08-25 19:11 全部完成（`H_aug_w32_s2` 中途被手動中止過一次，
從 `ckpt.pt` 的 epoch 30 續跑，不是重跑）。
判準與數字出自 `exp/results/capacity_summary.txt`。

| Q1 差距 | base=16（6 顆種子） | base=32（3 顆種子） | 隨寬度 |
|---|---|---|---|
| 1. 增強 − 基線 | +0.0185 t=7.56 未過閘 | **+0.0399 t=8.25 過閘** | **+0.0214 變大** |
| 2. 拓樸損失 − 基線 | **+0.0186 t=12.55 過閘** | −0.0040 t=−1.93 未過閘 | **−0.0227 消失** |
| 3. 增強 − 拓樸損失 | −0.0002 t=−0.06 未過閘 | **+0.0439 t=10.52 過閘** | +0.0441 變大 |
| 4.（Q4）增強 − 基線 | −0.0006 未過閘 | +0.0014 未過閘 | 兩邊都沒有 |

### 6.1 這個實驗要防的那個解釋，沒有成立

第 0 節寫的擔心是：[[e14_augmentation]] 的排序（**看什麼比要求什麼重要**）
可能只是「模型小到會過擬合二十張圖」的產物，
增強在替容量頂罪。如果是這樣，差距 1 會隨寬度**縮向零**。

它變大了，從 +0.0185 到 +0.0399。**方向跟那個解釋相反。**
容量給得越多，增強越值錢，不是越不值錢。

### 6.2 但另一個 arm 塌了，而那正是 E13 原本要問的

差距 2 是這個實驗最早的問題：**有了容量之後，損失函數會不會開始重要？**

答案是相反的。clDice 對 BCE+Dice 的優勢在 base=16 是 +0.0186、六顆種子全同號、
t=12.55，是整個系列裡最乾淨的過閘之一；到 base=32 變成 **−0.0040**，
三顆種子 [+0.0019, −0.0166, +0.0026]，均值為負且不過閘。
誠實的讀法是**與零無法區分，且不排除為負**。

也就是說，stage 0 的 E5 說「損失函數差別不大」，
這裡把它推到更強的形式：**那點差別本身就是小模型效應。**
拓樸損失買到的東西，容量也買得到，而且容量買得比較好。

### 6.3 差距 3 是最乾淨的一句話

在 base=16，增強和拓樸損失**打平**（−0.0002，t=−0.06）。
這正是 [[e14_augmentation]] 當時的處境：兩條路殊途同歸，難分高下。

在 base=32，增強贏 **+0.0439**，t=10.52，三顆種子全同號。

**同一組資料、同一個判準，只換了模型寬度，一個平手變成了單方面勝利。**
E14 的排序不但不是小模型的產物，它在小模型上是被**低估**的。

### 6.4 轉移測試給了一個獨立的佐證

E13 只看 DRIVE 內部。但同一批 w32 檢查點在 [[e17_transfer]] 的零樣本測試裡
（2026-08-25 補測，見該篇修訂區塊）呈現同一個形狀，而且更尖銳：

| | STARE β₀ 誤差 | HRF β₀ 誤差 |
|---|---|---|
| A_dice → A_dice_w32 | 145.0 → **178.0（變差）** | 599.7 → **674.1（變差）** |
| B_cldice → B_cldice_w32 | 113.2 → **140.4（變差）** | 496.7 → **589.0（變差）** |
| H_aug → H_aug_w32 | 79.3 → **73.4（變好）** | 384.9 → **368.2（變好）** |

**沒有增強的時候，加寬度讓轉移變差；有增強的時候，加寬度讓轉移變好。**
這是過擬合的教科書形狀，而且它是在 E13 之外的資料集上、
用 E13 沒有參與設計的判準看到的。

### 6.5 還沒被解決的限制

第 5 節寫的兩條限制**一條都沒有消失**：

**三顆種子仍然是三顆種子。** base=32 那一欄全部建立在三顆種子上，
而差距 1 的 seed 2 是 +0.0797，是另外兩顆（+0.0289、+0.0111）的三到七倍。
均值被一顆種子拉高的風險是真的。

**還有一件事要說清楚**：差距 1 在 base=16 那格印的是「未過閘」，
擋下它的是六顆種子裡的一顆 −0.0021。那個數字實質是零，不是反向證據。
但判準就是判準，**它沒過就是沒過**，不能因為結論好看就改讀法。
這也表示表格第一列嚴格說是「一邊沒過閘、一邊過閘」，
比「兩邊都過、差距變大」弱一階。

**4 倍不是 256 倍**這條也還在。117k → 467k，離 3000 萬還很遠。
這個實驗說的是「差距對容量的一階敏感度」，
**不是「在一個真正大的模型上會怎樣」**。

### 6.6 對後續的影響

E13 原本是要決定「要不要回頭投資損失函數」。答案是**不要**。
在這個容量區間裡，損失函數的優勢會被容量吃掉，增強的優勢不會。
[[e18_gate_plus_augmentation]] 的 `K_focal_aug` 之所以還值得留著，
不是因為它的 clDice 加權，是因為它**帶著增強**，
而它贏過 `H_aug` 的部分要看該篇和 [[e17_transfer]] 的修訂區塊，那裡分得更細。
