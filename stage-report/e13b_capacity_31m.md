# E13b · 容量曲線的第三個點（3100 萬參數）

2026-08-26 在實驗室 GPU 機器（2 × RTX 4070 Ti）上跑完。
十五次訓練（三個 arm × seed 0–4），約 3 小時 45 分。
判準沿用 `exp/summarize_capacity.py`，第三個點的後綴與參數量斷言
**寫在第一次 `_w64_d5` 訓練之前**，該檔先跑過 `--selftest` 才排隊。

**本篇不改寫 [[e13_capacity]] 的任何一個字。** 第 3 節記錄的是那篇的
數字在重訓後沒有重現，該怎麼處理留給後續決定。

---

## 0. 這一點要回答什麼

[[e13_capacity]] 有兩個點：117k 與 467k。它自己的第 5 節與 6.5 節寫得很清楚：

> **4 倍不是 256 倍。** 117k → 467k 仍然離 3000 萬很遠。
> 這個實驗說的是「差距對容量的一階敏感度」，
> **不是「在一個真正大的模型上會怎樣」**。

第三個點就是去掉這條限制。

## 1. 架構：五層 base=64，不是加寬的三層

**31,042,369 個參數**，`test_capacity.py` 以 `28e6 < n < 34e6` 斷言。

`TinyUNet` 原本寫死三層。要用它到 3000 萬得用 `base=256`，那會讓每一個
參數都待在 48×48 全解析度上 —— 最貴的花法，而且審稿人不接受這個架構。
標準 U-Net 用**五層 base=64** 到 ~31M，多出來的容量住在 6×6 和 3×3，
每個參數幾乎不花計算量。

深度和寬度一樣從 run 名稱讀出（`_w64_d5`），`build_model()` 仍是唯一決定
架構的地方。模組名稱刻意組成與手寫三層版本完全相同（`enc1..encN` /
`down1..` / `up1..` / `dec1..` / `head`），舊 checkpoint 照樣載得進去。

`predict_full()` 原本把影像 padding 到 4 的倍數（兩次降採樣寫死的），
五層需要 16 的倍數，改成從模型讀 `depth` 算出來。

## 2. 結果

`exp/results/capacity3_summary.txt`。Q1 = 最暗的對比層。

| Q1 差距 | base=16（6 種子） | base=32（3 種子） | **31M/d5（5 種子）** |
|---|---|---|---|
| 1. 增強 − 基線 | +0.0116 t=4.45 未過閘 | **+0.0415 t=10.97 過閘** | **+0.0523 t=11.67 過閘** |
| 2. 拓樸損失 − 基線 | +0.0021 t=1.53 未過閘 | −0.0211 t=−6.84 未過閘 | −0.0110 t=−3.11 未過閘 |
| 3. 增強 − 拓樸損失 | +0.0096 t=3.94 未過閘 | **+0.0625 t=12.55 過閘** | **+0.0633 t=15.21 過閘** |
| 4.（Q4）增強 − 基線 | +0.0008 未過閘 | +0.0001 未過閘 | −0.0020 未過閘 |

### 2.1 差距 1：趨勢延續，但在減速

+0.0116 → +0.0415 → +0.0523。單調變大，且在兩個較大的容量上都過閘
（31M 五顆種子全正）。**「增強是在補償一個太小的模型」這個解釋，
在真實模型尺寸上仍然不成立。**

但兩段的增幅是 **+0.0298** 與 **+0.0108**：從 117k 到 467k 的增幅是
從 467k 到 31M 的近三倍，而後者是 64 倍的參數。**效應在飽和。**

### 2.2 差距 2：拓樸損失在任何一個容量上都沒有過閘

+0.0021 → −0.0211 → −0.0110，三個容量全部未過閘。
31M 的五顆種子是 [−0.0525, +0.0025, −0.0198, +0.0429, −0.0281]，
**均值為負、符號不一致**。誠實的讀法是**與零無法區分**。

E13 原本要問「有了容量之後損失函數會不會開始重要」。
三個點之後的答案是：**在這個容量範圍內，沒有任何一點看得到它重要。**

### 2.3 差距 3 在 467k 之後就平了

+0.0096 → +0.0625 → **+0.0633**。第二段只動了 **+0.0007**。

「增強勝過拓樸損失」這件事在 467k 就已經到位，再給 64 倍參數不會讓它
更明顯。這是三條裡最乾淨的一句話，也是最該寫進論文的一句。

### 2.4 種子分散度是這一點的主要弱點

31M 差距 1 的五顆種子：[+0.0004, +0.0121, +0.0719, +0.0936, +0.0833]。
最大是最小的 **230 倍**。全部同號所以過閘，但均值由其中三顆撐起來，
另外兩顆實質是零。差距 3 同樣分散（+0.0096 到 +0.1114）。

**過閘不等於效應穩定。** 這裡需要的是更多種子，不是更多容量。

## 3. ⚠️ 重訓沒有重現 [[e13_capacity]] 的 base=16 判定

`*.pt` 被 gitignore，所以這台機器上一個 checkpoint 都沒有，前兩個容量點的
27 個 run 全部重訓過（同 config、同 seed、不同機器）。重訓後：

| Q1 差距 | 已發表（筆電） | 重訓（GPU） | 判定 |
|---|---|---|---|
| base=16 差距 1 | +0.0185 t=7.56 未過閘 | +0.0116 t=4.45 未過閘 | 相同 |
| **base=16 差距 2** | **+0.0186 t=12.55 過閘** | **+0.0021 t=1.53 未過閘** | **翻轉** |
| base=16 差距 3 | −0.0002 t=−0.06 未過閘 | +0.0096 t=3.94 未過閘 | 相同 |
| base=32 差距 1 | +0.0399 t=8.25 過閘 | +0.0415 t=10.97 過閘 | 相同 |
| base=32 差距 2 | −0.0040 t=−1.93 未過閘 | −0.0211 t=−6.84 未過閘 | 相同 |
| base=32 差距 3 | +0.0439 t=10.52 過閘 | +0.0625 t=12.55 過閘 | 相同 |

**七格裡六格的判定不變，翻掉的那一格是 [[e13_capacity]] 稱為
「整個系列裡最乾淨的過閘之一」的那一個。**

已發表的六顆種子全部同號、t=12.55；重訓的六顆是
[+0.0075, −0.0051, −0.0054, +0.0162, +0.0057, −0.0065]，三正三負。

**這不是移植 bug。** 兩個佐證：
- base=32 的三格判定全部重現，方向與量級都對得上。
- Task 0 的驗收（`A_dice_s0` 移開重跑）顯示 GPU 重現 CPU 的全影像 Dice
  到 **0.0002**，逐 epoch 的 loss 曲線也對齊。
- 11,520 列的逐列稽核：與筆電舊列的平均差 **+0.00017**，無系統性偏移
  （逐列散布是真的，4.2% 的列差超過 0.02 —— 重訓是**另一次訓練**，
  不是重新評分同一組權重）。

最可能的解釋：**+0.0186 這個效應小到，另一組六次訓練就重現不出來。**
配對 t 檢定量的是「同一個模型在不同影像上一致」，種子閘擋的是
「不同訓練之間符號翻轉」—— 兩者都通過了，但兩組各六次的訓練仍然給出
+0.0186（6/6 正）與 +0.0021（3/6 正）。這是教訓四的下一層：
**種子閘的門檻是「六顆同號」，而六顆同號在小效應上不是穩定的性質。**

**這需要決定怎麼處理，本篇不擅自決定。** 三個選項：
(a) 兩組數字並列，說明 [[e13_capacity]] 的差距 2 未能重現；
(b) 再跑一組六顆種子當裁判；
(c) 提高種子閘的門檻（例如要求兩組獨立的六顆）。

## 4. 兩種訓練協定，都要報

31M 上固定 100 epoch 不再中立。基線臂的訓練 loss 從 0.4164 掉到 0.1917，
驗證 Dice 從 0.8204 掉到 0.8044，β₀ 誤差從 63 漲到 135 —— **比 117k 網路的
89.6 還差**。有增強的那臂沒有這個現象。

最佳 epoch 的落點本身就是結果（seed 0）：

| arm | 最佳 epoch | best Dice |
|---|---|---|
| `A_dice_w64_d5` | **10** | 0.8204 |
| `B_cldice_w64_d5` | **30** | 0.8194 |
| `H_aug_w64_d5` | **80** | 0.8280 |

**拓樸損失把過擬合推遲了 20 個 epoch，增強推遲了 70 個。**

只報 epoch 100，會把「基線過擬合了 90 個 epoch」算進「增強的優勢」。
所以每一次訓練同時存 `final.pt`（epoch 100）與 `best.pt`（驗證 Dice 最高
的 epoch），選擇規則（用 Dice、不是拓樸指標）**寫死在程式碼裡、在任何一個
run 被它評分之前**。

**上面第 2 節的表全部是 `final.pt` 協定**，也就是與前兩個點相同的協定。
`best.pt` 的評分管線還沒接（`stratify.py` 目前只讀 `final.pt`），
72 個權重都在磁碟上，不需要重訓。

一個警訊：基線的最佳點落在**第一個驗證點**（epoch 10），表示真正的最佳
可能更早，被 `VAL_EVERY=10` 的取樣間隔錯過了。`best.pt` 是
「已驗證過的 epoch 中最好的」，不是「真正最好的」。

## 5. 成本

實測，不是外推（`exp/bench_step.py`）：

| | 參數 | ms/step | 每個 run |
|---|---|---|---|
| base=16 | 117k | 14.9 | 8 min |
| base=32 | 467k | 15.0 | 8 min |
| 31M/d5（BCE+Dice） | 31.0M | 23.5 | 13–14 min |
| 31M/d5（拓樸損失） | 31.0M | 30.5 | 16–17 min |

`prompt.md` 第 4 節估的 40–80 分鐘偏悲觀 3–5 倍。
小網路只有 5.6 倍加速（44.5 → 8 分）因為 117k 吃不滿 4070 Ti，
瓶頸在 numpy 資料管線 —— 該管線佔一個 step 的 1–2%，**不要改寫成
DataLoader**，這在 `prompt.md` 4.1 已經量過。

十五次訓練 3 小時 45 分；連同 57 個 checkpoint 復原共 72 次訓練，
兩張卡約 7 小時。
