# 我們的 ERL 跟領域參考實作算的是同一件事嗎

2026-08-28。`exp/erl_reference.py`，純 CPU，已跑完。

## 問題

不是「我們的數字好不好」，而是「我們的數字是不是讀者以為的那個意思」。
本 repo 每一個 ERL 都會被拿去跟已發表的 ERL 比，而讀者假設只有一種定義。

**參考實作**是 Allen Institute 的 `segmentation-skeleton-metrics`
（PyPI v5.9.3），連結體學 ERL 文獻用的那一個。它的公式在
`skeleton_metrics.py:643`，忽略 merge 時等於 `sum(l_i²) / sum(l_i)`。
我們的（`erl.py:71`）是 `sum(l_i²) / skel_gt.sum()`。

## 三個差異

1. **分母。** 它加總**已覆蓋**的片段；`node_labels()` 明確丟掉 label `"0"`
   —— 也就是預測從來沒找到的那段真實血管。我們除以完整骨架。
   所以一條完全漏掉的血管會扣我們的分，對它是隱形的。
   我們是比較小、比較嚴格的數字。
2. **Merge。** 一塊預測跨越兩個不同真實物件時，它記 0 分。我們沒有 merge 懲罰
   —— 視網膜影像是一棵連通的血管樹，沒有兩個物件可以合併。這是量測結果，不是假設。
3. **split vs bridged。** 我們在任何未覆蓋的中線像素處斷開一段，包括預測其實
   繞過去接起來的那種。`erl_convention.py` 已經量過這一項，列在這裡是為了不要混淆。

## 精確關係

`ours = reference × coverage`，在每一個測試案例上都成立到浮點誤差以內
（`--selftest` 斷言之）。所以任何一個已發表的數字都可以事後換算，
只要 coverage 一起報。

## 量測結果

規則 (iv)、報告半，六顆種子：

| 臂 | 我們的 | 參考實作 | bridged | coverage |
|---|---|---|---|---|
| `A_dice` | 32.4% | 39.2% | 59.8% | 81.9% |
| `H_aug` | 34.3% | 41.4% | 60.6% | 81.9% |
| `G_focal` | 39.9% | 47.1% | 63.2% | 84.1% |
| `K_focal_aug` | **47.4%** | **54.5%** | **67.3%** | 86.0% |

**頭條數字會因為約定不同差 7 個百分點，而且領域的參考實作給的是比較高的那個。**
排序在三種約定下都不變，所以每一個臂之間的比較都不受影響 —— 受影響的只有絕對值。

## 後果

論文必須明講用哪一種，並且把 coverage 那一欄放在旁邊。
用參考實作的約定報 54.5% 是合法的，而且是讀者預期的；
但不附 coverage 就等於把「有 14% 的血管根本沒找到」藏起來。

建議：**主表報參考實作約定（54.5%），coverage 當相鄰欄位**，
我們自己的嚴格版本放在補充材料，並說明兩者的精確關係。

## 這個腳本不做的事

它**沒有**執行參考套件本身。那個套件吃 SWC 骨架與 label volume，
走的是為 3D 連結體學建的 graph pipeline；把 DRIVE 搬進去會變成在測試
那個搬運，而不是在測試指標。公式短到可以逐行抄，抄本用手算的案例斷言過
（全覆蓋兩者相同、一刀切開 38.025 vs 39.000、漏掉一半 20.0 vs 40.0）。

## 修訂 2026-09-03 —— 「排序不變」這一條被推翻

上面的結論「三種約定下臂與臂的排序都不變」在它自己的範圍內仍然成立，
但那個範圍比當時寫的窄：**4 個臂、pre-heldout 協定、而且只沿分母這一個軸比。**

`exp/erl_spec.py`（見 [erl_spec.md](erl_spec.md)）在 held-out 協定、10 個臂、
12 顆種子下，把三個軸**交叉**起來量。以本報告的參考格 `split/edges/covered`
為基準，最遠的一格 `bridged/diameter/covered` 的 Spearman ρ = **−0.103**，
最大名次移動 **7 名**（`H_aug_clw64`）。也就是排序在那兩格之間沒有關係。

原因是本報告沒有量到的交互作用：**切分規則的正負號取決於長度約定**
（bridged > split 在 pixels/edges 是 10/10，在 diameter 是 0/10）。
只沿一個軸移動看不到它。

本報告的數字與 `ours = reference × coverage` 這個恆等式不受影響，
恆等式在 erl_spec 的 selftest 裡逐圖重新斷言過。**受影響的只有排序那一句。**

## 修訂 2026-09-04 —— 參考實作**自己就有兩個分母**，這比原本的說法更有利

原文（08-28）說：「他們只加總已覆蓋的片段（`node_labels()` 丟掉 label 0），
我們除以完整骨架」，並把這寫成**我們 vs 他們**的差異。

今天為了填「從來沒真的跑過參考套件」這個缺口，下載了
`segmentation_skeleton_metrics-5.9.5`（PyPI wheel）並讀了原始碼。
**原文的描述不完整**，而遺漏的那一半對論文是好消息。

### 證據

`skeleton_metrics.py:644-671`（原文引用的那段，確認無誤）：

```python
def compute_graph_erl(graph):
    ...
    for label in graph.node_labels():          # 丟掉 "0"
        run_length = graph.run_length_from(nodes[0])
        wgts.append(run_length)
        run_lengths.append(0 if label in graph.labels_with_merge
                           else run_length)
    return np.average(run_lengths, weights=wgts)
```

**但同一個檔案 `skeleton_metrics.py:857` 還有第二個輸出：**

```python
normalized_erl = results["ERL"][name] / graph.run_length
```

`graph.run_length`（`graph_classes.py:79` 初始化，由 `physical_dist` 累加）
是**完整真值骨架的長度**。

### 這代表什麼

同一個套件同時吐出兩個數字，分母不同：

| 套件輸出 | 式子 | 分母 |
|---|---|---|
| `ERL` | `Σlᵢ² / Σlᵢ(covered)` | **已覆蓋**片段 |
| `normalized ERL` | `ERL / L_full` | 用**完整**骨架再正規化一次 |

代數上（`L_cov = coverage × L_full`）：

```
我們報的分數      = Σlᵢ² / L_full²
他們的 normalized = Σlᵢ² / (L_cov × L_full)
→  我們的 = 他們的 normalized × coverage
```

**恆等式的形式跟原文一樣，只是往上挪了一層**，原文的
`ours = reference × coverage` 仍然成立（那是對 raw `ERL` 講的）。

### 對論文的影響——變好，不是變壞

原本的敘事是「我們跟參考實作的分母不一樣」，那會被讀成**我們偏離了標準**。
實際情況是：**參考實作本身就吐出兩個分母不同的數字，而引用「ERL」的論文
不會說自己用的是哪一個。** 這正好是本論文主張的東西：
**欠定不是我們造成的，欠定在參考實作裡就已經存在。**

### 仍然未做

**還是沒有真的執行過那個套件。** 它的輸入是 3D 的 SWC 骨架與 label volume，
把 DRIVE 移植進去會變成在測那個移植。可行且值得做的是：
**在手算得出答案的合成案例上跑他們的程式，驗證我們的抄寫與他們的輸出相同**
——這樣測的是抄寫，不是移植。列為待辦，尚未實作。在那之前，論文引用參考
實作的定義時必須說明「依原始碼轉寫，未執行原套件」。

## 修訂 2026-09-05 —— **真的執行了參考套件**，結果比預期重要得多

上一段修訂結尾寫「還是沒有真的執行過那個套件……列為待辦」。已經做掉了。
`exp/erl_reference_check.py`，對 `segmentation-skeleton-metrics 5.9.5`。

### 做法（避開移植問題）

沒有把 DRIVE 移植進他們的 SWC/volume 管線。改成**直接從骨架影像 + 預測
建出他們的 `LabeledGraph`**：一個骨架像素一個節點、8-鄰接連邊、
`node_voxel = (0, row, col)`（他們的 `physical_dist` 是體素座標的歐氏距離，
所以正交步 = 1、對角步 = √2，正好是我們的 `edges` 約定）、
`node_label` = 覆蓋該像素的預測連通塊 id，未覆蓋則 `"0"`。
然後直接呼叫他們自己的 `ERLMetric.compute_graph_erl`。
**受測的是我們的抄寫，不是移植。**

### 結果一：公式的抄寫是對的

直線斷裂的合成案例上，他們的 `ERL` 與我們的 `(split, edges, covered)`
**浮點等值**，六個案例皆然，且 `full == covered × coverage` 逐案成立。
加權平均的算式、覆蓋分母、邊長幾何三者都驗過了。

（先驗過他們的函式本身：6 節點直線 → 5.0；斷成邊長 2 與 1 → 1.6667
＝ `(2²+1²)/(2+1)`，與手算相同。）

### 結果二：他們的迴圈有一個**連通性前提**，在 2D 血管上代價巨大

```python
for label in graph.node_labels():
    nodes = graph.nodes_with_label(label)
    run_length = graph.run_length_from(nodes[0])   # 只走 nodes[0] 那一塊
```

`run_length_from` 只走**含 nodes[0] 的那個同標籤連通塊**。若某標籤的骨架節點
在骨架上是**斷開的**，其餘的塊完全不被計算。他們的載入器
（`graph_loading.py:357-406` `_label_graph`）直接指派分割標籤，**沒有把斷開
標籤拆開的步驟**——所以這是他們函式的真實行為。

在 3D 連結體學這個前提通常成立（一個分割出來的神經元只在一處碰到真值骨架）。
**在視網膜上不成立**，因為一個好的預測是**一整塊**連通血管，而它覆蓋到的骨架
在有斷口的地方就是斷開的。用真實訓練模型（`H_aug_s0` @0.5）量：

| 影像 | 斷開的標籤數 | **未被走到的已覆蓋骨架節點** | 他們的 ERL（原始） | 重標籤後 |
|---|---|---|---|---|
| 01 | 8 | **97.8%**（8356 中） | **21.81** | 6394.21 |
| 02 | 14 | 13.7%（8096 中） | 7874.06 | 6929.71 |
| 03 | 17 | **95.3%**（6781 中） | **33.47** | 1033.64 |

**影像 01 上差了約 300 倍。** 而且誤差不是固定偏差，是隨資料變動的
（13.7% 到 97.8%）。

### 結果三（最重要）：他們的片段長度**取決於節點列出的順序**

`run_length_from` 走的是 DFS 生成樹，每到一個新節點就把「走過來的那條邊」
加進去，而且**保留每一條對角邊**。骨架圖只要有環（樓梯形、L 形轉角，
8-鄰接下遍地都是），生成樹就不唯一，長度就跟著節點順序跑。

最小案例：三個像素的 L 形轉角 `(0,0) (0,1) (1,1)`，8-鄰接下是一個三角形。
六種節點排列下他們的 ERL：

```
2.0        2.0        2.414214   2.414214   2.414214   2.414214
```

**同一個三像素圖形，只因為點被列出的先後不同，答案在 2.0 和 2.414 之間跳。**
在他們的管線裡那個順序就是 SWC 檔案裡點的順序。

我們的 `edges` 約定在兩個正交替代路徑存在時會丟掉斜邊
（`erl_length.edge_list`），所以**六種排列都是 2.0**。

這也解釋了結果一在真實影像上的殘差：修好連通性之後，他們的數字仍比我們大
**+0.76% 到 +1.71%**（9 次比較），來源就是這些沒被去重的斜邊。

### 對論文的影響

原本這一節是「我們跟參考實作的分母不一樣」，一個防守性的說明。
現在它是**論文裡最有力的一節之一**，而且是只有真的把程式跑起來才拿得到的：

1. **欠定不是我們造成的。** 同一個套件吐出兩個分母不同的數字（前一段修訂）。
2. **參考實作帶一個沒有寫下來的前提**（每個標籤在真值骨架上必須連通），
   這個前提在 connectomics 默默成立、在視網膜上不成立，代價在我們的資料上
   最壞是 97.8% 的骨架不被計算。
3. **連「片段的長度」都不是良定義的**：在有環的骨架圖上，參考實作的答案
   取決於輸入順序。

所以規格論文要規定的不只是三個約定，還要規定**「片段長度必須與輸入順序無關」**
以及**「標籤在真值骨架上必須連通，否則先拆開」**。這兩條是這次跑出來的。

### 誠實的界線

- 這是對 **5.9.5** 版量的，`VERIFIED_AGAINST` 常數記在腳本裡。
- 我們建圖的方式是**我們**對「他們的資料長什麼樣」的重建。結果二說的是
  「把預測連通塊當標籤餵給他們的函式會發生什麼」，那是他們載入器的行為
  （已讀 `_label_graph` 確認沒有拆分步驟），但不是在他們的 3D 資料上實測的。
- 結果三不依賴任何重建：那是他們的函式在一個三節點圖上的行為，直接可重現。
