# 閾值 0.5 買到的東西，有多少是方法，有多少是校準

2026-08-31。`exp/frontier.py`、`exp/calibration.py`。360 個 run × 33 個閾值，
訓練全部在 `--protocol heldout` 下。

## 問題

本系列每一個分割都是 `prob >= 0.5`。**0.5 沒有任何理由，只有慣例。**

掃過閾值之後發現：**各臂的 Dice 峰值不在同一個閾值上**，而且差得很遠。

| 臂 | Dice 峰值所在的閾值 |
|---|---|
| `A_dice_w32` | 0.325 |
| `A_dice` | 0.377 |
| `K_focal_aug` | 0.662 |
| `H_aug_clw64` | 0.798 |

`K_focal_aug` 系統性地**低估自己的信心** —— focal 閘專門在模型猶豫的地方加重
拓樸項，把機率分布壓平。所以在 0.5 這一刀，它預測出比自己最佳點更多的前景。

**而多預測前景本身就會買到連通性。** 所以在 0.5 比較各臂，比的可能不是方法，
是「誰的機率分布剛好偏離 0.5 比較多」。

## 做法

每個臂讀兩次：

1. 在慣例的閾值 **0.5**。
2. 在讓它自己的 **dev Dice** 最大的閾值。

兩次都在 20 張 test 影像上讀 traced fraction。閾值從 **dev** 曲線挑，
只在 test 上讀出 —— 在 test 上挑閾值，跟先前修掉的檢查點洩漏是同一個毛病、
只是低一層：在報告用的集合上調的閾值，會讓報出來的數字變成 33 次抽樣的最大值。

判準三分類：

- **frontier** —— 在自己的最佳操作點上仍然領先且過閘。這是方法效應。
- **calibration** —— 只在共用的 0.5 領先。這是校準位移。
- **nothing** —— 兩種讀法都不領先。

## 三個結論

### 1. 我們自己的兩個貢獻是校準假象

`G_focal`（信心閘）和 `K_focal_aug`（信心閘 + 增強）在 0.5 上分別領先
+6.1% 和 +13.6%，兩者都過閘。在各自最佳操作點上是 **−2.2% 和 −4.2%** ——
不只消失，是**反過來輸**。

機制說得通而且是自洽的：信心閘的作用就是在模型猶豫處加重拓樸項，
那必然把機率分布壓平，必然把 Dice 峰值推離 0.5。E18 的頭條
「可追蹤長度 27.5% → 46.1%」很可能主要是這件事。

### 2. 已發表的損失在這個讀法下全部是零

`B_cldice`、`E_cbdice`、`C_boundary`、`D_blurpool`、`I_coletra`、`J_liot`，
以及 31M 的容量提升，在自己的最佳操作點上對 `A_dice` 的差距全部落在
−1.8% 到 +1.4% 之間，一個都沒過閘。

### 3. 撐住的只有「增強 + 中線加權」

`H_aug_clw*` 這一族在**每一個權重**上都是 frontier 且過閘（+2.5% 到 +6.1%）。
`K_focal_aug_clw16/32/64` 也是。

但這條線有前人做過 —— Skeleton Recall Loss（ECCV 2024），
見 `stage-report/novelty_check.md`。

## 權重掃描為什麼找不到峰值

掃到 64 仍然單調上升（`H_aug_clw64 − H_aug` = +2773.6 ERL，t = 40.96）。
**因為原始 ERL 不是正確的軸。** Dice 代價同步爆炸：

| 權重 | ΔERL | ΔDice | = 幾個種子標準差 |
|---|---|---|---|
| 4 | +340.6 | −0.0019 | −2.2 |
| 8 | +721.9 | −0.0059 | −6.9 |
| 16 | +1232.2 | −0.0166 | −19.3 |
| 32 | +1849.3 | −0.0351 | −40.8 |
| 64 | +2773.6 | −0.0682 | **−79.3** |

（`H_aug` 基底，十二顆種子）

**`clw` 是取捨旋鈕，不是改進。** 轉大一點就多換一點連通性、多付一點 Dice。
問「哪個權重最好」在原始 ERL 上沒有答案；在匹配成本下才有，
而在那裡它確實是 frontier。

## 事前登記狀態，誠實說明

- **`frontier.py` 是事前登記的。** 四條預測寫在 docstring 裡，
  兩分支規則在任何 run 之前就固定了。
- **`calibration.py` 是事後的。** 我是看到前緣掃描才想到的。
  它在自己的輸出第一行就印 `POST-HOC`。
- 兩者結論一致，但**確認的權重不同**。`calibration.py` 的結果應該被當成
  「值得再做一次事前登記驗證的假設」，不是已確認的結論。

## 這次抓到的自己的錯

**前緣的第一版在 test 曲線上挑閾值。** 那跟剛修掉的檢查點洩漏是同一個毛病、
低一層。已改為從 dev 曲線挑、只在 test 上讀出。

**pre-registered 的保守分支答錯了問題。** 它取「容差內最高的閾值」，
也就是前景比 Dice 峰值**更少**的那一側 —— 那量的是「過度閾值化有多糟」，
不是「拿 Dice 換連通性能買到什麼」。generous 分支（前景更多的那側）
在 2026-08-30 事後補上，**標為修訂而不是替換**，因為看到結果之後改規則
正是事前登記制度要讓它可見的那件事。兩個分支都報。
